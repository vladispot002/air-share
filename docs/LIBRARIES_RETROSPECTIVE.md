# Ретроспектива використання зовнішніх бібліотек та фреймворків

Цей документ містить аналітичний звіт-ретроспективу за результатами виконання **Лабораторної роботи №3** з дисципліни *«Парадигма об'єктно-орієнтованого програмування»* у межах розробки кросплатформної системи передачі даних **LAN-Drop**.

У межах лабораторної роботи було поставлено завдання інтегрувати зовнішні бібліотеки/фреймворки (що не входять до стандартної бібліотеки C++ STL і не дублюють навчальний стек, як-от Qt з ЛР2 чи тестові фреймворки), розібравшись з їхньою документацією та практичним використанням.

Для реалізації завдань безпеки, збереження конфігурації та мережевої взаємодії було обрано дві ключові промислові бібліотеки:
1. **`nlohmann/json` (JSON for Modern C++)** — бібліотека для обробки та серіалізації даних у форматі JSON.
2. **`OpenSSL 3` (`libssl` та `libcrypto`)** — галузевий стандарт криптографічних примітивів, хешування та транспортної безпеки TLS 1.3.

---

## 1. Бібліотека `nlohmann/json` (JSON for Modern C++)

### 1.1. Які конкретні задачі планувалося вирішувати за допомогою бібліотеки?
У процесі розвитку LAN-Drop виникла необхідність у надійному та стандартизованому форматі представлення структурованих даних для трьох ключових підсистем:
- **Збереження конфігурації застосунку (`SettingsPresenter`)**: збереження та відновлення налаштувань користувача (робочий порт, ліміт швидкості, режим автоприйому файлів, оформлення інтерфейсу) у файлі `~/.config/landrop/settings.json` із забезпеченням зворотної сумісності та стійкості до пошкодження файлу.
- **Взаємодія з хмарними релеями (`CloudPeer`)**: формування запитів до REST API та парсинг відповідей про ліміти сховища (`storage_quota_bytes`, `used_storage_bytes`).
- **Сумісність із протоколами мобільного обміну (`AirDropProtocolBridge`)**: генерація та валідація JSON-корисного навантаження для емуляції запитів `/Discover` та `/Ask`.

**Потрібні можливості бібліотеки**:
- Зручна та безпечна типізація під час десеріалізації.
- Підтримка парсингу без аварійного завершення (fail-safe parsing) при роботі з некоректними даними.
- Інтуїтивний C++20-синтаксис для роботи з вкладеними об'єктами й масивами.

---

### 1.2. Чому було обрано саме `nlohmann/json`, а не аналоги?
Під час проєктування розглядалися такі альтернативи:
1. **`RapidJSON`**:
   - *Переваги*: максимальна швидкість роботи та низьке споживання пам'яті завдяки SAX/DOM парсингу.
   - *Чому відхилили*: громіздкий, C-подібний DOM API, високий поріг входження, надлишковий код для типових операцій читання/запису конфігурацій. Для обсягів даних конфігурацій та REST-повідомлень (до кількох кілобайтів) екстремальна продуктивність SAX не є критичною.
2. **`Boost.PropertyTree` / `Boost.JSON`**:
   - *Чому відхилили*: підключення Boost створило б надважку зовнішню залежність заради однієї утилітарної задачі, суттєво уповільнивши конфігурацію CMake та час збірки в CI/CD.
3. **`QJsonDocument` / `QJsonObject` (Qt Core)**:
   - *Чому відхилили*: хоча Qt використовувався у ЛР2 для інтерфейсу, модулі ядра LAN-Drop (`landrop_core`) проєктувалися як незалежні від GUI, здатні компілюватися для headless CLI (`lan_drop send`/`receive`). Використання `QJsonDocument` порушило б чисту архітектуру шарів та вимоги лабораторної роботи щодо застосування самостійних сторонніх бібліотек.
4. **Власний парсер рядків**:
   - *Чому відхилили*: написання власного синтаксичного аналізатора JSON є неефективним дублюванням коду, схильним до вразливостей (path traversal, некоректне екранування лапок, unicode-символів тощо).

**Обґрунтування вибору**: `nlohmann/json` став ідеальним компромісом: він має повністю ідіоматичний дизайн для сучасного C++ (STL-like контейнери, підтримка ініціалізаторів списків, перевантажені оператори), високу надійність і ліцензію MIT.

---

### 1.3. Наскільки просто було отримати, налаштувати та почати використовувати?
- **Отримання та інтеграція**: Бібліотека є *header-only* (розповсюджується у вигляді одного заголовного файлу `nlohmann/json.hpp`). Ми додали заголовок до директорії `include/nlohmann/json.hpp`. Це не вимагало окремого лінкування у `CMakeLists.txt` чи додаткових бінарних файлів, що зробило кросплатформну збірку під Linux, Windows та macOS тривіальною.
- **Труднощі та їх вирішення**:
  1. *Обробка помилок парсингу*: За замовчуванням виклик `json::parse()` викидає виняток `nlohmann::json::parse_error` у разі пошкодженого JSON. Щоб запобігти неконтрольованому аварійному завершенню застосунку при читанні зламаного файлу налаштувань, ми використали перевантаження без винятків:
     ```cpp
     auto j = nlohmann::json::parse(jsonContent, nullptr, false);
     if (j.is_discarded()) {
         // Застосування значень за замовчуванням
         return false;
     }
     ```
  2. *Час компіляції*: Через інтенсивне використання метапрограмування на шаблонах включення `json.hpp` у спільні заголовні файли збільшувало час компіляції всього проєкту. Проблему вирішено суворим архітектурним правилом: включати `json.hpp` виключно у файли реалізації (`.cpp`), не засмічуючи публічні інтерфейси класів.

---

### 1.4. Оцінка документації та корисність ресурсів
- **Офіційна документація (`json.nlohmann.me`)**: Оцінюється як зразкова. Кожен метод супроводжується робочим прикладом коду, показує часову складність та можливі винятки.
- **Сильні сторони**:
  - Розділ *«Integration»* чітко пояснює всі способи підключення (CMake FetchContent, vcpkg, conan, single-header).
  - Наочні приклади перетворення типів через `get<T>()`, `value("key", default_val)` та використання макросів `NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE`.
- **Слабкі сторони**: Інформація про те, як повністю вимкнути винятки (`JSON_NOEXCEPTION`) або використовувати парсер з прапорцем `allow_exceptions = false`, дещо розпорошена по розділах розширених налаштувань.

## 2. Бібліотека `OpenSSL 3` (`libssl` та `libcrypto`)

### 2.1. Які конкретні задачі планувалося вирішувати за допомогою бібліотеки?
Передача файлів у локальній мережі або через публічний Інтернет без шифрування є вразливою до перехоплення трафіку (eavesdropping), атак «людина посередині» (MITM) та несанкціонованої модифікації файлів.

**Задачі, покладені на OpenSSL**:
1. **Транспортна безпека (TLS 1.3)**: Створення класу `TlsContext` та інтеграція з `NetworkSession` для повноцінного двостороннього шифрування сокетних з'єднань із сучасними шифрокомплектами (`TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`).
2. **Автентифікація пристроїв та пінінг сертифікатів**: Генерація самопідписаних X.509-сертифікатів у пам'яті (`TlsHelper::generateCertificate`), обчислення їхніх SHA-256 відбитків (fingerprint) та верифікація за принципом Certificate Pinning без потреби в платному глобальному CA.
3. **Криптографічна автентифікація PIN-коду спільного каталогу (`SharedFolderManager`)**: Захист PIN-коду за допомогою галузевого стандарту **PBKDF2-HMAC-SHA256** (16 байтів криптостійкої солі `RAND_bytes`, 100 000 ітерацій) та безпечне порівняння за сталий час за допомогою `CRYPTO_memcmp` для захисту від timing attacks.
4. **Контроль цілісності файлів (`FileChunkHasher`)**: Обчислення контрольних сум файлів і потокових блоків через криптографічний інтерфейс SHA-256 (EVP API).
5. **Захищений клієнт HTTPS (`HttpClient`)**: Взаємодія з хмарними серверами та верифікація ланцюжків сертифікатів через системне сховище CA (`X509_V_FLAG_CRL_CHECK`).

---

### 2.2. Чому було обрано саме `OpenSSL 3`, а не аналоги?
Розглядалися такі альтернативи:
1. **`mbedTLS`**:
   - *Переваги*: компактний розмір, розрахований на вбудовані системи.
   - *Чому відхилили*: інтеграція із системними сховищами сертифікатів на рівні ОС Linux (Fedora/Debian) менш тривіальна, відсутні багато високооптимізованих асемблерних інструкцій (AES-NI) «з коробки», менш поширена в репозиторіях дистрибутивів порівняно з OpenSSL.
2. **`GnuTLS`**:
   - *Чому відхилили*: ліцензійні обмеження LGPL/GPL, складніша інтеграція на платформах Windows (MSVC), незвичний стиль API.
3. **`Crypto++`**:
   - *Чому відхилили*: чудова бібліотека для математики та алгоритмів хешування, але вона **не містить реалізації протоколу TLS/SSL**. Тобто для реалізації шифрованого сокетного каналу все одно довелося б писати чи шукати додатковий TLS-рушій.
4. **`QtNetwork` (`QSslSocket`)**:
   - *Чому відхилили*: для чистоти архітектури ядра (`landrop_core`) ми уникали залежності від Qt в мережевому рушії. Крім того, під капотом `QSslSocket` у Linux все одно динамічно завантажує той самий OpenSSL через `dlopen`.

**Обґрунтування вибору**: OpenSSL 3 є стандартом де-факто для операційних систем Linux, має підтримку апаратного прискорення криптографії, найактуальнішу реалізацію TLS 1.3, повний набір сертифікованих примітивів (PBKDF2, EVP, X.509, CSPRNG) та встановлений практично на кожному робочому вузлі.

---

### 2.3. Наскільки просто було отримати, налаштувати та почати використовувати?
- **Підключення до проєкту**:
  У `CMakeLists.txt` підключення було реалізовано стандартним модулем:
  ```cmake
  find_package(OpenSSL REQUIRED)
  target_link_libraries(landrop_core PUBLIC OpenSSL::SSL OpenSSL::Crypto)
  ```
  Для платформи Fedora встановлювався пакет `openssl-devel`, для Ubuntu — `libssl-dev`.

- **Труднощі та специфіка використання**:
  1. *Перехід на OpenSSL 3.0 API*:
     У версії OpenSSL 3 застаріли низькорівневі функції минулих років (наприклад, `SHA256_Init`, `RSA_generate_key_ex` тощо). Ми свідомо уникнули застарілих викликів і реалізували хешування через сучасний уніфікований EVP API (`EVP_MD_CTX_new`, `EVP_DigestInit_ex`, `EVP_DigestUpdate`, `EVP_DigestFinal_ex`).
  2. *Керування ресурсами (C-style memory management)*:
     OpenSSL написаний на C, тому вимагає обов'язкового парного виклику деструкторів (`SSL_free`, `SSL_CTX_free`, `X509_free`, `EVP_MD_CTX_free`). Для забезпечення суворої гарантії відсутності витоків пам'яті (RAII) у C++20 коді LAN-Drop було реалізовано власні структури-вартові (`SslCtxGuard`, `SslGuard`, `SocketGuard`) та інтелектуальні вказівники із кастомними делетерами:
     ```cpp
     std::unique_ptr<EVP_MD_CTX, decltype(&EVP_MD_CTX_free)> ctx(EVP_MD_CTX_new(), EVP_MD_CTX_free);
     ```
  3. *Неблокуючий режим сокетів (Handshake State Machine)*:
     При роботі з сокетами в неблокуючому режимі виклики `SSL_connect` та `SSL_accept` можуть повертати помилки `SSL_ERROR_WANT_READ` або `SSL_ERROR_WANT_WRITE`. Довелося коректно реалізувати цикл очікування подій на сокеті з таймаутами через `select()`/`poll()`.

---

### 2.4. Оцінка документації та корисність ресурсів
- **Офіційна документація**: Складається з детальних man-сторінок (розділи `man 3 ssl`, `man 3 crypto`).
- **Сильні сторони**:
  - Бездоганний і вичерпний опис параметрів кожної окремої функції, кодів повернення та прапорців помилок у `ERR_get_error()`.
  - Офіційний документ *«OpenSSL 3.0 Migration Guide»* дуже допоміг уникнути застарілих підходів попередньої гілки 1.1.1.
- **Слабкі сторони**:
  - Практично відсутні наскрізні приклади для сучасного C++: більшість прикладів написані в стилі C 1990-х років із використанням `goto err`.
  - Багатошарова концепція структур (BIO, X509_STORE, SSL_CTX, SSL) вимагає значного часу для побудови ментальної моделі взаємодії об'єктів.
- **Допоміжні ресурси**:
  - Репозиторій прикладів OpenSSL (`openssl/demos`).
  - Статті та обговорення на StackOverflow щодо валідації hostname через `X509_check_host` та запобігання атакам за часом через `CRYPTO_memcmp`.

## 3. Синергія бібліотек у проєкті

Бібліотеки `nlohmann/json` та `OpenSSL 3` у проєкті LAN-Drop склали взаємодоповнюючий стек для безпечного обміну даними:
1. **Криптографічний захист каналу + структурований протокол**: `OpenSSL 3` забезпечує безпечну транспортну трубу (TLS 1.3 сокет або HTTPS-запит), а `nlohmann/json` відповідає за безпечний вміст цього каналу (серіалізація та валідація корисного навантаження).
2. **Відсутність дублювання функціоналу**: Жодна з бібліотек не перетинається за призначенням, разом вони забезпечують компактне, повністю незалежне від GUI ядро системи (`landrop_core`).

## 4. Загальний висновок та отриманий досвід

Інтеграція зовнішніх бібліотек `nlohmann/json` та `OpenSSL 3` у межах Лабораторної роботи №3 повністю виправдала себе:
- **`nlohmann/json`** продемонструвала, яким має бути ідеальний сучасний C++ інструмент: нульова вартість конфігурації (header-only), виразна семантика коду та зручність, наближена до високорівневих мов на кшталт Python або TypeScript.
- **`OpenSSL 3`** дала глибоке розуміння того, як інтегрувати низькорівневі C-бібліотеки системного рівня в сучасний безпечний C++20 проєкт через парадигму RAII, як працюють сертифікати X.509, механізми пінінгу та запобігання атакам за часом.

**Що варто було б зробити так само**:
- Використовувати `EVP` API замість застарілих функцій OpenSSL.
- Обмежувати область підключення важких заголовків виключно файлами реалізації (`.cpp`).
- Застосовувати власні RAII-обгортки для роботи з C-вказівниками.

**Що можна було б змінити або покращити**:
- Для OpenSSL було б доцільно оформити невелику внутрішню бібліотеку-обгортку (C++ RAII wrapper library) з готовими класами `UniqueSslBio`, `UniqueSslCtx`, що зменшило б кількість рутинного boilerplate-коду в різних мережевих класах проєкту.

### Довідка: підтверджуючі факти та файли проєкту
Висновки та аналіз, наведені у цій ретроспективі, безпосередньо ґрунтуються на вихідному коді репозиторію LAN-Drop:
1. `include/nlohmann/json.hpp` — підключена бібліотека JSON for Modern C++.
2. `src/ui/SettingsPresenter.cpp` — використання `nlohmann::json` для стійкого збереження та читання налаштувань.
3. `src/peers/CloudPeer.cpp` — серіалізація REST-запитів квот.
4. `src/mobile/AirDropProtocolBridge.cpp` — валідація JSON-повідомлень `/Ask`.
5. `include/landrop/core/TlsContext.hpp` та `src/core/TlsContext.cpp` — налаштування TLS 1.3, контекстів `SSL_CTX`, генерація сертифікатів X.509 та обчислення SHA-256 fingerprint через OpenSSL.
6. `src/core/NetworkSession.cpp` — робота з неблокуючими TLS-сокетами (`SSL_read`, `SSL_write`, пінінг відбитків).
7. `src/core/SharedFolderManager.cpp` — застосування `PKCS5_PBKDF2_HMAC`, `RAND_bytes` та `CRYPTO_memcmp` для криптозахисту PIN-коду доступу.
8. `src/core/FileChunkHasher.cpp` — реалізація хешування SHA-256 через OpenSSL EVP API.
9. `src/core/HttpClient.cpp` — клієнтський стек HTTPS на базі сокетів та OpenSSL.
10. `CMakeLists.txt` (рядки 53–73) — директиви `find_package(OpenSSL REQUIRED)` та лінкування з `landrop_core`.
11. `tests/unit_tests.cpp` (набори `testJsonAndRestSerialization` та `testTlsTransportAndDeviceAuth`) — автоматизовані модульні тести, що перевіряють коректність інтеграції обох бібліотек.
